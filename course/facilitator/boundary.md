# Backstage: the note boundary

Not part of default context or automatically served by the workbench. Supply when the learner requests design detail or the resolution. This is a candidate opening; the learner's actual frustration has not yet been supplied.

**Encounter.** An actual rough note, plus an optional explicitly staged harmless fixture. The learner recognises their own text and chooses what using it should accomplish. Unresolved connection: saved application state and usable model context can differ. Do not claim that every mismatch is this boundary.

**Prerequisites.** Saving/exporting a note and an available model route. Tested bridge instruments: revision selector, exact context preview, run receipt, output, export, draft edition. Native Open WebUI attachment, Notes, retrieval and skill loading need account-level verification. No access to hidden reasoning or provider internals.

**Intervention space.** No selection versus explicit selection; an older versus newer revision; a deliberately conflicting note; a revised question. Keep model/config fixed while distinguishing transport from interpretation. When native Notes works, compare note-side chat, chat attachments and Knowledge individually. A second model is useful after transport is understood, not as an uncontrolled pile of changes.

**Evidence and alternatives.** The request can establish which text was sent by this client. A correct answer alone cannot establish retrieval or training. A missing answer could be omitted context, output truncation, poor instruction following, conflicting evidence, a model limitation or an unavailable route. A provider token count is not a proof that every instruction was followed. Trace boundaries before prescribing a fix. Do not turn a local app trace into a claim about Open WebUI's native pipeline.

**Optional help, immediately available.** Pointer: compare the selected revision with the request. Instrument: open the JSON messages. Full explanation: a saved note is application state; a stateless request contains only the supplied messages, and sending a note does not train model weights. Retrieval and tools can select text for a later request, but each has its own failure modes. This explanation is supplied material. If the learner asks for a fix, provide it and record scope, then return control of the investigation.

**Capability.** Locate a boundary and demonstrate a discriminating intervention, or diagnose and bound an unavailable feature. Evidence may be an actual request comparison, a repair trace, a learner-designed equivalent or a supported negative finding. Scope it to the model, configuration and environment. Downstream reason: retrieval and agent debugging become unreliable if transport and behaviour are conflated. No recitation required. Review is proposed; record the learner response, contest or bypass. Supplying the instrument is not evidence that the learner understands it.

**Persistence.** Original note, changed revision, actual request/output, interpretation separately attributed, and an optional reusable recipe. Link failures and corrections with `contradicts` or `builds_on`. Possible connections: selection, revision freshness, token budget, retrieval, conflicting instructions. The learner need not choose any of these.

**Test the encounter.** Ask what was useful or tedious after use, not as an entrance form. Record their actual words as learner feedback and the subsequent design change separately. No feedback has yet been observed. If the puzzle is merely unclear controls or broken plumbing, repair those directly. Keep the broader commission alive.
